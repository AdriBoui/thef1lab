Un pipeline de données, c'est une chaîne de montage : on part d'une source de données extérieure, et à chaque poste on la rapproche d'un état exploitable. Ton projet suit le schéma le plus courant aujourd'hui en entreprise, appelé ELT — Extract, Load, Transform.

ELT vs ETL

ETL (l'ancienne école) transformait la donnée avant de la charger. ELT (aujourd'hui) charge d'abord le brut dans l'entrepôt, puis transforme à l'intérieur avec du SQL. C'est justement ce que tu fais : ton métier actuel de Data Integration, c'est le « EL » ; dbt t'ajoute le « T ». C'est la brique qui te fait passer Data Integration → Data Engineer.

Le vocabulaire à maîtriser

Ces mots reviendront en entretien. Les comprendre sur ton projet vaut mieux que de les réciter.

Pipeline de donnéesdata pipeline
L'enchaînement automatisé qui amène la donnée de la source jusqu'au tableau de bord. Le projet entier est un pipeline.
Entrepôt de donnéesdata warehouse
Une base pensée pour l'analyse (pas pour une appli). Ici c'est BigQuery. On y stocke et on y calcule.
Couche bruteraw layer
La copie fidèle de la source, sans modification. On peut tout reconstruire à partir d'elle : c'est le filet de sécurité.
Modélisationdata modeling
Organiser la donnée en tables qui ont un sens métier. C'est le savoir-faire qui distingue un Data Engineer.
Table de faitsfact table
Les événements mesurables : un tour, un arrêt au stand, un résultat. Beaucoup de lignes, des chiffres. Ex. fact_laps.
Table de dimensiondimension table
Le contexte descriptif : un pilote, une session, un circuit. Peu de lignes. Ex. dim_driver.
Idempotenceidempotency
Relancer le pipeline deux fois donne le même résultat — pas de doublons. Assurée ici par le full refresh.
Orchestrationorchestration
Ce qui décide quand et dans quel ordre le pipeline s'exécute. dbt ne se lance pas seul : GitHub Actions le déclenche.
03

Chaque poste de la chaîne

① Extraction — le script Python

Un client interroge l'API OpenF1 dans l'ordre logique : d'abord les meetings (week-ends de course), puis les sessions de chacun, puis pour chaque session les tours, relais, arrêts, météo et résultats. L'API impose une limite stricte (30 requêtes/minute) : on espace donc les appels de 2,2 s. C'est ce qui rend le run long — pas le volume, qui reste minuscule.

CE QU'ON ÉVITE

On n'ingère pas la télémétrie brute (car_data, location) : elle échantillonne chaque voiture ~3,7 fois/seconde, soit des millions de lignes. C'est un choix délibéré pour rester dans le quota gratuit de BigQuery.

② Chargement — la couche raw dans BigQuery

Le script écrit chaque endpoint dans une table raw_*. On fait un full refresh : à chaque run, on écrase et on recharge tout. Pour une saison (quelques dizaines de Mo) c'est plus simple qu'un chargement incrémental, et ça garantit l'idempotence.

③ Transformation staging — le nettoyage (dbt)

Chaque modèle stg_*.sql lit une table brute et la remet d'équerre : conversion des dates en vrais timestamps, sélection des colonnes utiles, renommage. Ce sont des vues (pas de stockage supplémentaire). C'est du SQL, pas du YAML.

④ Transformation marts — le modèle métier (dbt)

On assemble le staging en un schéma en étoile : des tables de faits (fact_laps, fact_pit_stops, fact_race_results) entourées de dimensions (dim_driver, dim_session, dim_meeting). C'est la forme que tous les outils de BI savent exploiter — d'où le calcul des points au championnat via un petit fichier de correspondance (seed).

⑤ Les tests — la qualité de la donnée (dbt)

Dans les fichiers schema.yml, on déclare des garde-fous : une clé est-elle unique et jamais nulle ? chaque tour pointe-t-il vers un pilote qui existe (relationships) ? Si un test échoue, le pipeline te prévient. C'est le signal fort recherché par les recruteurs : tu ne produis pas seulement de la donnée, tu prouves qu'elle est fiable.

⑥ Orchestration — GitHub Actions

Un fichier de workflow lance, chaque jour, la séquence complète : ingestion → dbt run → dbt test. Ça tourne sur les serveurs de GitHub, gratuitement, même ton ordinateur éteint.

⑦ Restitution — Looker Studio

On branche Looker Studio directement sur le dataset marts. Comme c'est du BigQuery natif, aucun serveur à héberger, et le rapport se partage par simple lien public.

06

Le cycle, une fois lancé

Ce qui se passe chaque jour, tout seul, à 4h du matin (UTC) :

# 1. Extraction + chargement — Python
python -m ingestion.run
   → écrase et recharge les tables raw_openf1.* dans BigQuery

# 2. Transformation — dbt
dbt seed   # charge le barème de points
dbt run    # construit staging (vues) puis marts (tables)
dbt test   # vérifie unicité, non-nullité, intégrité

# 3. Restitution — automatique
→ Looker Studio lit les marts à jour au prochain rafraîchissement
À RETENIR

Trois responsabilités séparées, et c'est voulu : Python extrait, dbt transforme et teste, GitHub Actions déclenche. Aucun outil ne fait le travail d'un autre — c'est ce découpage propre qui rend un pipeline lisible et maintenable.
